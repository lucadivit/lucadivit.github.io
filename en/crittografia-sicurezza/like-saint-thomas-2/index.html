In the previous article we saw what homomorphic encryption is. Hard to believe, right? Go tell Saint Thomas. So by now we should know that we can perform computations on encrypted data without having to decrypt it. Yeah, fine, but in practice? That is what I want to tackle in this article, and we will do it by concretely implementing an algorithm. There is an embarrassing amount of choice, so why not make life difficult? Go CKKS (Cheon-Kim-Kim-Song), I choose you.

One Step At A Time

Before we start, it is good to make one thing clear: implementing CKKS for real, in the sense of "now I am going to write myself a secure, efficient, production-ready library", is a great way to do yourself harm. CKKS is not just "two additions, two multiplications and done". Inside it there are polynomial rings, noise, scaling, rescaling, relinearization, modulus switching, encoding on complex vectors, and a whole series of details that, if tackled all at once, turn an educational article into a criminal complaint against mathematics. So we will do something more sensible: we will proceed one step at a time. In this article (or rather, series of articles) we will not implement a complete and secure version of CKKS, but a toy version. A Toy CKKS, if we want to give it an international name so everything sounds more serious. The goal is not to build something to actually use for encrypting your company's data, your bank's data, or your misdeeds. The goal is to understand how the fundamental building blocks of the scheme are connected to one another. So we will start from the basics:

  • we will build a polynomial ring of the form \(R_q = \mathbb{Z}_q[x] / (x^N + 1)\)
  • we will implement addition and multiplication between polynomials
  • we will use these polynomials to build an RLWE-based encryption
  • we will add a very simple encoding to represent real numbers
  • we will try to perform additions and multiplications directly on ciphertexts
  • we will observe what happens to scale and noise after the operations.

In other words, we will not start from full CKKS. We will start from what is needed to get there without losing our sanity along the way. So the first stop is the polynomial ring.

(Where) They Live

No, I am not talking about the aliens from the movie. For now the only "they" we care about are our messages. But what are these mysterious messages? I would love to tell you that they are text strings, made up of characters belonging to a conventional alphabet, but it is not that simple. I could say they are numbers, but that would also be a lie. In reality, messages are represented as polynomials. And not just any polynomials, but polynomials with integer coefficients modulo a certain number \(q\). More specifically, these messages are the elements belonging to a polynomial ring of the form

\[ R_q = \mathbb{Z}_q[x] / (x^N + 1) \]

Formula 1. Polynomial Ring

I do not know whether you remember, but we already talked about polynomial rings here. There is, however, an important distinction to make. In the case of cyclic codes, the \(N\) of the ring could be any positive integer, while in the case of CKKS, \(N\) must be a power of two. I have already written this in other articles, so you should know it by now, but today I am feeling generous and I will repeat it. Working with a polynomial ring means that I will have polynomials whose coefficients are integers modulo \(q\) and that, when I multiply two polynomials, the result is reduced modulo \(x^N + 1\), coming back inside the ring itself. It differs from a field because the existence of a multiplicative inverse is not guaranteed. I will not tell you more than that, otherwise go read it here. So our messages are inside a fenced area, and every time a message tries to climb over the boundary, it gets brutally thrown back in.

The Polynomial Fence

I know that saying messages live in

\[ R_q = \mathbb{Z}_q[x] / (x^N + 1) \]

gets you dates, but we also need to be practical. So let us give this thing a shape and turn what we said into code.

class PolynomialRing:

    ...

    def create(self, coefficients: list[int]) -> list[int]:
        reduced_coefficients = [coefficient % self._modulus for coefficient in coefficients]

        if len(reduced_coefficients) < self._degree:
            reduced_coefficients += [0] * (self._degree - len(reduced_coefficients))

        return self.reduce(reduced_coefficients)

    def reduce(self, coefficients: list[int]) -> list[int]:
        result = coefficients[:]

        while len(result) > self._degree:
            coefficient = result.pop()
            target_index = len(result) - self._degree
            result[target_index] -= coefficient

        return [coefficient % self._modulus for coefficient in result]

    def add(self, first: list[int], second: list[int]) -> list[int]:
        first = self.create(first)
        second = self.create(second)
        return [(first[index] + second[index]) % self._modulus for index in range(self._degree)]

    def multiply(self, first: list[int], second: list[int]) -> list[int]:
        first = self.create(first)
        second = self.create(second)
        product = [0] * (2 * self._degree - 1)

        for first_index, first_coefficient in enumerate(first):
            for second_index, second_coefficient in enumerate(second):
                product[first_index + second_index] += (first_coefficient * second_coefficient)

        return self.reduce(product)

Snippet 1. PolynomialRing Class

And using it, we get:

q = 17
n = 4

ring = PolynomialRing(degree=n, modulus=q)

# p(x) = 18x^4 + 4x^3 + 3x^2 + 2x + 1
coefficients = [1, 2, 3, 4, 18]
polynomial = ring.create(coefficients=coefficients)

print(f"Anello polinomiale: R_{q} = Z_{q}[x] / (x^{n} + 1)")
# 4x^3 + 3x^2 + 2x
print(f"p(x) mod (x^{n} + 1):", ring.format(polynomial))

Snippet 2. Reduction in a Polynomial Ring

This snippet should print p(x) mod (x^4 + 1): 4x^3 + 3x^2 + 2x, which is the result of reducing \(p(x)\) modulo \(x^N + 1\). The result comes from two distinct reductions. First we reduce the coefficients \(\pmod{q}\), so \(18 \equiv 1 \pmod{17}\). Then we reduce the polynomial modulo \((x^N+1)\). Since in this ring \(x^4 \equiv -1\), the term \(x^4\) cancels the constant term \(1\), leaving \(4x^3+3x^2+2x\). And just like that, the starting polynomial (which tried to leave the fence since its degree was greater than or equal to \(N\)) gets brutally thrown back into \(R_q\).

Adding And Multiplying Inside The Fence

Now that we understand how to bring a polynomial back inside our fence, we can start doing something more interesting: adding and multiplying polynomials. Addition is fairly calm. If we add two polynomials, we add the coefficients of terms of the same degree and then reduce everything modulo \(q\). Hard to mess up, or at least not more than I usually do, like being born.

Multiplication, on the other hand, is slightly more interesting. When we multiply two polynomials, the degree of the result can exceed \((N - 1)\). And when that happens, we have to reduce the result modulo the polynomial to get back into \(R_q\). Let us look at an example with the polynomials \(a(x) = 2x^2 + 2x + 3\) and \(b(x) = 15x^2 + 1\), in the polynomial ring \(R_{17} = \mathbb{Z}_{17}[x] / (x^4 + 1)\) defined in Snippet 2.

  • Addition:
\[ \begin{aligned} a(x) + b(x) &= 17x^2 + 2x + 4 \\ &\equiv 2x + 4 \pmod{17} \end{aligned} \]
  • Multiplication:
\[ \begin{aligned} a(x) \cdot b(x) &= (2x^2 + 2x + 3) \cdot (15x^2 + 1) \\ &= 30x^4 + 30x^3 + 47x^2 + 2x + 3 \\ &\equiv 13x^4 + 13x^3 + 13x^2 + 2x + 3 \pmod{17} \\ &\equiv -13 + 13x^3 + 13x^2 + 2x + 3 \pmod{x^4 + 1} \\ &= 13x^3 + 13x^2 + 2x - 10 \\ &\equiv 13x^3 + 13x^2 + 2x + 7 \pmod{17} \end{aligned} \]

Let us include the snippet for these operations as well:

q = 17
N = 4

ring = PolynomialRing(degree=N, modulus=q)

# a(x) = 2x^2 + 2x + 3
a = ring.create(coefficients=[3, 2, 2])
# b(x) = 15x^2 + 1
b = ring.create(coefficients=[1, 0, 15])

sum_result = ring.add(first=a, second=b)
product_result = ring.multiply(first=a, second=b)

# a(x) + b(x): 2x + 4
print("a(x) + b(x):", ring.format(sum_result))
# a(x) * b(x): 13x^3 + 13x^2 + 2x + 7
print("a(x) * b(x):", ring.format(product_result))

Snippet 3. Addition and Multiplication in a Polynomial Ring

Messages, Scales, And Approximations

We started working inside a polynomial ring: we saw how to reduce, add, and multiply polynomials while respecting the fence rule. But we cannot stay forever in the comfort zone of integers. From the article on finite fields, we know that we can bring a rational number into a finite field, we just need to find its multiplicative inverse. The point is that rings, by definition, do not require a multiplicative inverse, and therefore it is not guaranteed to exist. That nice little speech about inverses, here, does not apply. So how do we represent real numbers? The answer is simple: we cannot. We can, however, represent approximated real numbers. And to do that, we will use a very simple encoding: we will multiply the real number by a scale \(s\) and round it to the nearest integer. In practice, given a real number \(m\), we choose a scale \(s\) and compute:

\[ \tilde{m} = \lfloor m \cdot s \rceil \]

Formula 2. Approximation Formula

Let us make this clear right away with an example. Given \(m=1.25\) and \(s=100\), we get:

\[ \tilde{m} = \lfloor 1.25 \cdot 100 \rceil = 125 \]

So we are no longer working with a real number, but with an integer

\[ 1.25 \rightarrow 125 \]

When we want to go back to the real number, we just divide by the scale \(s\):

\[ m = \frac{\tilde{m}}{s} \]

Formula 3. Inverse Approximation Formula

And so, going back to the example, we get:

\[ m = \frac{125}{100} = 1.25 \]

So far everything is clear and clean. But since luck has not been sailing my sea for years, does it really make sense to think we will always receive only numbers with \(2\) decimal digits? Of course not. And what happens when we receive a number with more than two decimal digits? Suppose, for example, we multiply two numbers:

\[ a = 1.23, \quad b = 1.01 \Rightarrow a \cdot b = 1.2423 \]

And we approximate using the same scale.

\[ \tilde{m} = \lfloor 1.2423 \cdot 100 \rceil = \lfloor 124.23 \rceil = 124 \]

and therefore, going back to the real number, we get:

\[ m = \frac{124}{100} = 1.24 \]

As you can see, the number is not the same. By approximating we lost information. And that is precisely why CKKS is said to be an approximate scheme. It does not promise to return the exact value, but a sufficiently close one. And it is the scale that controls the precision of the approximation. A larger scale means greater precision, but also greater risks (as we will see). And here too, let's introduce our nice little class:

class Encoder:

    ...

    def encode_value(self, value: float) -> int:
        return round(value * self._scale)

    def decode_value(self, value: int) -> float:
        return value / self._scale

    def encode(self, values: list[float]) -> list[int]:
        coefficients = [self.encode_value(value) for value in values]
        coefficients.reverse()
        return self._polynomial_ring.create(coefficients)

    def decode(self, polynomial: list[int], expected_length: int) -> list[float]:
        coefficients = polynomial[:expected_length]
        coefficients.reverse()
        return [self.decode_value(coefficient) for coefficient in coefficients]

Snippet 4. Encoder Class

The Price Of Precision

Increasing the scale allows us to preserve more decimal digits, but to quote Sebastiano Barisoni, in economics there are no free lunches. The reason is simple: the larger the scale, the larger the integer that represents our real number also becomes. Suppose we want to encode \(m = 1.2345\). If we want to preserve it without losing decimal digits, we can choose a scale \(s = 10\,000\) obtaining:

\[ \tilde{m} = 1.2345 \cdot 10\,000 = 12\,345 \]

The problem is that the coefficients of our polynomials live modulo \(q\). So if we choose a modulus that is too small, the encoded value gets reduced modulo \(q\) and no longer represents the number we thought we had encoded. For example, if \(q = 17\), then:

\[ 12\,345 \bmod 17 = 3 \]

You can easily see that \(3\) is not exactly the best way to remember that we wanted to represent \(1.2345\). This is where headroom comes into play, meaning the margin of space we leave between the values we want to represent and the modulus \(q\). This margin is needed because, during operations, intermediate values can grow. If we already start too close to the modulus, it takes very little to get a modular reduction that completely changes the meaning of the encoded value. In short: the scale buys precision, but it consumes space inside the modulus. The more precision we want, the more carefully we must choose \(q\).

q = 17
N = 4
scale = 10

ring = PolynomialRing(degree=N, modulus=q)
encoder = Encoder(scale=scale, polynomial_ring=ring)

for value in [1.2, 1.83]:
    scaled_value = encoder.encode_value(value)
    encoded_value = scaled_value % q
    decoded_value = encoder.decode_value(encoded_value)
    # [1.2, 1.83]
    print("Messaggio originale:", value)
    # [12, 18]
    print("Messaggio scalato:", scaled_value)
    # [12 % 17 = 12, 18 % 17 = 1]
    print("Messaggio codificato modulo q:", encoded_value)
    # [12 / 10 = 1.2, 1 / 10 = 0.1]
    print("Messaggio decodificato:", decoded_value)
    print()

Snippet 5. Approximation of a Real Number via Scaling

In this example the second value is intentionally problematic. With \(q = 17\) and \(s = 10\), the number \(1.83\) is first turned into \(18\), but then \(18 \bmod 17 \equiv 1\). So when decoding we get \(0.1\), not \(1.83\). The function is not wrong: we are the ones who chose a modulus that is too small relative to the scale and the values we want to represent.

Giving Value To Our Message

At this point let us pretend we want to transmit, or process, a message without leaving it in the clear. Let us say that our starting message is the vector:

\[ m = [1.2,\ 0.5,\ 2.1] \]

Be careful though, this vector is not yet a message in the sense of the scheme. It is only the set of real values we want to start from. To make it live inside our system we first have to transform it into something compatible with the polynomial ring \(R_q\). The first step is to apply the scale to each element of the vector. Let us choose:

\[ s = 10 \]

and compute:

\[ \tilde{m} = [12,\ 5,\ 21] \]

Now we have a vector of scaled integers. But even this is not yet the final message: it is only an intermediate representation. The message, in our case, must be an element of the ring \(R_q\). For this reason we take these values and use them as the coefficients of a polynomial. Looking at the previous snippets, it is easy to guess that the polynomial representing our message will be:

\[ m(x) = 12x^2 + 5x + 21 \]

q = 23
N = 4
scale = 10

ring = PolynomialRing(degree=N, modulus=q)
encoder = Encoder(scale=scale, polynomial_ring=ring)

message = [1.2, 0.5, 2.1]
message_polynomial = encoder.encode(values=message)
# 12x^2 + 5x + 21
print("Messaggio nell'anello:", ring.format(message_polynomial))

Snippet 6. Message Creation

Let me point out that this is still not the full CKKS encoding. There is still some water that has to pass under the bridge before we get there, but it gives a rough idea of what is going on.

Now that a real vector has become a polynomial inside \(R_q\), we can use the same operations defined earlier. We do not have to invent anything new: adding two messages means adding their respective polynomials in the ring, and multiplying them means multiplying their respective polynomials and reducing the result modulo \(x^N + 1\).

q = 23
n = 4
scale = 10

ring = PolynomialRing(degree=n, modulus=q)
encoder = Encoder(scale=scale, polynomial_ring=ring)

m1 = [1.2, 0.5, 2.1]
m2 = [0.3, 1.0, 0.4]
poly_m1 = encoder.encode(values=m1)
poly_m2 = encoder.encode(values=m2)

sum_polynomial = ring.add(first=poly_m1, second=poly_m2)
product_polynomial = ring.multiply(first=poly_m1, second=poly_m2)

# 12x^2 + 5x + 21
print("m1 nell'anello:", ring.format(poly_m1))
# 3x^2 + 10x + 4
print("m2 nell'anello:", ring.format(poly_m2))
# 15x^2 + 15x + 2
print("Somma nell'anello:", ring.format(sum_polynomial))
# 20x^3 + 2
print("Prodotto nell'anello:", ring.format(product_polynomial))

Snippet 7. Operations Between Messages in the Ring

Addition is easy to interpret, because it preserves the scale. Multiplication, on the other hand, is nasty. In fact, by multiplying two values scaled by \(s\), the result will have scale \(s^2\). And that is where the next problem comes from (which do not worry, we will not tackle today).
